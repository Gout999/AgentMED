# AgentMED 文档盘点与产品取舍

> 状态：新项目产品考古记录，不属于旧仓库的运行或施工权威
>
> 日期：2026-08-13
>
> 目的：从 AgentMED 历代文档中恢复产品原始意图，明确新项目 PRD 继承什么、修正什么、舍弃什么。

## 1. 盘点结论

AgentMED 最值得保留的不是旧仓库里的版本号、对象数量和施工阶段，而是下面四个产品判断：

1. **产品定位正确**：AgentMED 不是客服系统，也不是 Agent runtime，而是 AI 应用发生 badcase 后的质量改进与安全变更系统。
2. **Agent Team 分工正确**：取证、归因、修复、独立验证、协调和经验沉淀必须由不同职责承担，避免同一个 Agent 自己提案、自己判卷、自己批准。
3. **端到端流程正确**：异常进入后，需要经过证据与版本绑定、调查、候选修复、独立验证、受控执行、观察与回滚，最后沉淀为回归资产。
4. **确定性与概率性分层正确**：Agent 负责分析、解释和起草；确定性系统负责状态、权限、幂等、审计、门禁和外部动作对账。

旧项目后期的问题不是这些判断失效，而是实现顺序逐渐从“用户完成一次可信修复”转向“先建设完整治理对象与施工证明系统”。新项目应回到前者。

## 3. 继承、修正与舍弃

| 早期设定 | 裁决 | 新项目表达 |
|---|---|---|
| AgentMED 是 AI 应用质量治理的 meta 层 | **保留** | 定位为 AI 应用 badcase 调查、可信修复和安全变更系统 |
| 客服只是第一被治理对象 | **保留** | 客服降为可选 Scenario Pack，不是产品身份 |
| 六角色 Agent Team | **保留并抽象** | 保留六类职责和权限隔离，不要求永远运行六个独立模型进程 |
| LLM 不拥有状态与权限 | **保留** | 确定性治理内核为唯一权威，Agent 只提交建议与工件 |
| 投诉→归因→修复→门禁→灰度→回复→沉淀 | **保留并泛化** | Signal→Case→Evidence/Version→Investigation→Candidate→Verification→Release/Observe/Recovery→RegressionAsset |
| 每个 Case 必须跑 5-cell/2³ 因果归因 | **修正** | 归因是按风险和可干预性启用的调查工具，不阻塞所有 Case；允许 `INCONCLUSIVE` |
| 修复候选直接形成 WorkOrder | **拆分** | Candidate 先独立验证；只有显式部署请求才产生 ReleasePlan/WorkOrder |
| 守门员一票否决 | **保留语义** | required Gate 未通过时任何人不能授权执行；守门员不能单独制造 PASS |
| 人工审批是发布强制关卡 | **保留** | 高风险动作必须由人批准 exact plan/hash/target/expiry |
| Trust Ledger + Wilson 自动晋升 | **后置** | 先做证据与策略历史；自治升级必须由真实 pilot 决定，不进入 MVP |
| 动态创建/缩容 Agent | **后置** | 角色调度是运行优化，不是首个产品价值 |
| AgentTeams 是产品必选编排层 | **舍弃绑定** | AgentTeams 可作为 Adapter；角色身份、权限和 receipt 才是产品要求 |
| 12 个角色专属 MCP projection | **舍弃实现形态** | 新项目使用少量 canonical intents 和按角色授权的薄 Adapter |
| 完整组件拓扑和 15 类 SystemComponent | **后置** | MVP 使用不可变、可扩展的 `VersionSnapshot`；真实需求再引入细粒度组件图 |
| Skill/MCP 自演化、Incident/SLO、成本和企业治理 | **未来扩展** | 只有核心修复闭环获得采用后再逐项准入 |
| 每条 Case 都自动部署 | **舍弃** | `VerifiedCandidate / NOT DEPLOYED` 是完整且有价值的终点 |

## 4. 新 PRD 的产品不变量

新实现可以完全重写，但不得破坏以下语义：

1. Agent 不得拥有权威生命周期状态、人工审批或高风险执行权限。
2. 原始 Signal、验收标准、版本、候选、评测和动作必须精确绑定，不能靠聊天上下文推断。
3. 预期状态、实际观察和已经发生的外部副作用必须分开记录。
4. required evidence 缺失、失败、不确定或不匹配时，不得生成可执行授权。
5. Candidate Verification PASS 只证明候选值得采用，不代表已经部署。
6. 发布授权必须绑定 exact ReleasePlan/WorkOrder，并由人或已验证的窄范围策略批准。
7. 外部动作结果不明时进入 `UNKNOWN` 并对账，不得臆断失败后盲目重试。
8. 每个关闭的 Case 应形成可复用的 RegressionAsset 和可追溯证据。
9. Agent Team 的价值来自职责、证据和权限分离，不来自 Agent 数量。
10. 所有 vendor、模型、runtime、trace source 和协作渠道都是可替换 Adapter。

## 5. 新项目的唯一产品入口

新项目应只把下列文档作为产品入口：

- [`AgentMED-产品需求文档.md`](AgentMED-产品需求文档.md)：完整产品定义、角色、流程、需求、MVP 和成功指标。

后续工程文档应从该 PRD 派生，而不是反过来通过数据库对象或施工阶段改写产品定义。
